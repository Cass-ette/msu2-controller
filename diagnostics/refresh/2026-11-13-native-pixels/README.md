# 共享像素处理优化与实测

日期：2026-11-13。本次优化 RGB565 转换及设备命令编码，减少每帧 Python 循环工作量。Windows、Mac 共用这两个函数，没有新增依赖。基线提交 `5991e71`，实现提交 `7707093`。

## 问题与方法

前一轮 [跨平台对照](../../../docs/refresh-comparison.md) 发现：直接 10 FPS 发送已明显流畅，但图像转换存在主机耗时及偶发长延迟。旧实现逐像素 `struct.pack()`，再为每个暂存槽逐条拼命令。

现在用 Pillow 原生查表和逐通道运算生成相同的大端 RGB565，再通过预置命令模板与切片填入数据。所有命令边界、末块有效长度、填充字节及输出摘要保持一致。Mac 继续 60 字节分块，Windows 继续大块写入；应答检查、GUI 调度及闪存写入节奏没有改变。

## 验证及结果

无硬件准备阶段比较由 [benchmark_pixel_pipeline.py](../../../benchmark_pixel_pipeline.py) 完成：固定、移动方块、彩色图各预热 20 轮，再各采 300 组配对样本；每轮交换旧/新先后顺序，逐次核对 RGB565 和命令载荷完全一致。原始数据见 [host-preparation.json](host-preparation.json)。

| 画面 | 旧准备耗时中位 ms | 新准备耗时中位 ms |
| --- | ---: | ---: |
| 固定白块 | 2.332 | 0.203 |
| 移动白块 | 2.336 | 0.202 |
| 彩色图 | 2.767 | 0.194 |

准备阶段减少约 91%–93%，不含串口通信。实机另用原 `benchmark_refresh.py` 未改的 10 FPS 循环依次测基线、新版，各固定 120 + 移动 120，共 480 帧；没有自动恢复、闪存写入或新增设备操作。

生成到通信检查完成的中位耗时约减少 4% / 8%。串口仍是主要耗时，目标仍为 10 FPS，不能把准备阶段的十余倍提速宣称为显示帧率提升十余倍。

原始实机数据为 [baseline-timing.json](baseline-timing.json) 和 [optimized-timing.json](optimized-timing.json)。两端每帧协议写入数集合均 `[6]`，读取数均 `[4]`。基线是从 `5991e71` 复制的四份未改文件，不带 `.git`，其原始 metadata 的 commit/dirty 为 null；记录的 `msu2.py` SHA-256 已与该提交核对。新版实测源码提交为 `7707093fa8fd85f3ff4b88999adc6186efccf7e9`，哈希为 `71c19b9fd6d5eee591bd3504532458002da16c0c05a94d1419dae4139b467e55`。完整汇总和文件摘要见 [summary.json](summary.json)。

这是一组顺序执行的实机对照，后台负载没有控制，硬件顺序没有交换。固定阶段新版 P95 更高，偶发长延迟仍在；旧移动最慢帧在图像转换与写入中均有大延迟。不能据此认定已解决系统调度或 USB 长尾。前一轮用户“明显流畅”的观察发生于此次优化之前，不作为新版的额外目视结果。没有测量 LCD 扫描完成时刻。

复测准备阶段时，指定优化前的本地源码目录：

```sh
python -B benchmark_pixel_pipeline.py --baseline-dir /path/to/baseline \
  --iterations 300 --output validation/pixel-preparation.json
```

两版实机对照在各源码目录调用同一份 `benchmark_refresh.py`，用 `--source-dir` 选择基线；每次关闭其他串口消费者，只计原始显示路径。原始公开文件不含端口序列号、用户名路径或设备素材。

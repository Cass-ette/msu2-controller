# Windows / Mac 刷新对照记录

后续已完成共享像素处理优化及新版实机比较，见 [实现、原始数据与安装包验证](../diagnostics/refresh/2026-11-13-native-pixels/README.md)。下文保留优化前的跨平台基线，不混用两种源码的计时。

日期：2026-11-13。Mac 已用 [Windows PR #1](https://github.com/Cass-ette/msu2-controller/pull/1) 的原计时循环完成三轮实机测试，共 720 帧，另采两帧主机调用跟踪。单帧生成到通信检查完成的中位数约 44–50 ms，与 Windows 的约 46 ms 相近；移动阶段帧起始间隔中位约 100 ms。第三轮应用户要求重播，用户确认“现在很明显流畅了很多”。

本节证据使用优化前的共享源码，正式传输、GUI 调度及固件均未改变，没有写入闪存。主机通信结束不等于 LCD 刷新完成，主机函数跟踪不等于 USB 总线抓包，也没有证明双缓冲。

## 问题、假设与验证

- **问题**：此前 Mac GUI 画面逐步更新的观感与 Windows 不同。历史 Mac 大载荷每 60 字节等待 1 ms；当前共享源码已保留分块、取消实时像素的分块等待，烧录仍采用保守节奏。
- **假设**：先统一测试画面、10 FPS 目标、计时边界和调用层级，检查直接传图路径是否仍有明显差异。GUI 的采样、生成、调度及预览需要分别测量，不能仅凭肉眼认定 USB 驱动或设备缓冲方式。
- **验证**：相同脚本直接调用各自原有 Display.show()，每组 120 帧，先固定白块再移动白块，Mac 原样运行三轮。调用跟踪独立执行；全部逐帧数据及长延迟均保存，没有挑选最好的一轮。

## 调用层级已核实

旧 Windows show() 在显示前 keep_alive() 额外读取宽、高；当前共享源码只有发送后的尺寸通信检查，因此少两写两读。

| 实测源码 / 平台（独立补采各两帧） | Display._write | serial.write | serial.read |
| --- | ---: | ---: | ---: |
| 旧 Windows | 8 | 8 | 6 |
| 共享源码 / Windows | 6 | 6 | 4 |
| 共享源码 / Mac | 6 | 655 | 4 |

Mac 三轮协议写入数集合均为 [6]、读取数集合均为 [4]。独立跟踪确认 39,000 字节像素拆成 650 次各 60 字节的底层写入，其他控制命令 5 次，共 655 次 serial.write，仍只有 6 次 _write。两帧跟踪均无短读、短写或 flush；计时脚本没有逐次记录底层返回长度，不能把补采证据扩展到每个计时帧。

## GUI 与后续范围

当前 GUI 投屏默认 5 FPS，可选 2/5/10；时钟、状态和功率约 1 秒请求画面，功率后台约 2 秒采样。Tk 每 20 ms 调度、10 ms 查工作结果，唯一串口线程忙时不启动其他任务，实体按键、保活和通知也参与调度。本轮直接传图没有经过 GUI，未量化这些环节的实际贡献。

后续优先减少共享图像转换与命令编码的主机工作量，保持像素字节、分包、应答和烧录节奏一致，再用相同脚本实测。GUI 若仍有差异，再分别测采样、生成、排队和发送；残余长延迟需交换测试顺序、记录负载。需要解释实体屏幕更新时刻时，应做 USB 总线跟踪和同一相机拍摄，并考虑滚动快门。

基线验证：--check 通过；test_refresh_benchmark、test_transport 共 6 项模拟测试通过。720 个计时帧及另两帧跟踪完成并关闭串口。Windows PR #1 仅包含诊断，不代表旧 Windows 全部功能已经合并。
